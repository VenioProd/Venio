# Venio Agent API — Codex instructions

> Drop this file at the root of any repo where Codex needs to call Venio (rename it `AGENTS.md`, or append its content to an existing `AGENTS.md`). Codex reads `AGENTS.md` automatically as project-level context.

## Reach Venio through ONE URL family

```
https://venio.paris/api/v1/agent/*
```

Do NOT try `/api/admin/*` or `/api/v1/*` (without `/agent`). Those are gated by user JWT sessions issued by the browser login — a Personal Access Token (`vno_pat_...`) is always rejected there with `401 Invalid token`. There is no fallback path.

## Auth header — only one form works

```http
Authorization: Bearer vno_pat_<32 chars base62>
```

The server reads exactly that header. The following do NOT work and will return 401:

- `x-admin-token: ...`
- `x-venio-token: ...`
- `x-api-key: ...`
- `Authorization: <token>` (without `Bearer `)

Do not retry with alternate header names. They are not implemented.

## First request to run on any new token

```bash
curl -sS -H "Authorization: Bearer $VENIO_AGENT_TOKEN" \
  https://venio.paris/api/v1/agent/ping
```

Interpret the result:

| Response | Meaning | Action |
|---|---|---|
| `200 { ok: true, name, prefix, scopes }` | Token valid. | Proceed. If a later call fails with 401, the URL is wrong, not the token. |
| `401 MISSING_TOKEN` | Header didn't arrive. | Verify `$VENIO_AGENT_TOKEN` is set; ensure `Bearer ` prefix. |
| `401 INVALID_TOKEN` | Revoked, mis-copied, or wrong env. | Regenerate in Venio's `/admin/agents` UI. Secret is shown only at creation. |
| `401 EXPIRED_TOKEN` | `expiresAt` passed. | Regenerate. |
| `403 INSUFFICIENT_SCOPE` | Token valid, but path needs a scope it lacks. | Response body shows `required`, `granted`, `missing`. Regenerate with the missing scopes. |

## URL rewrites (admin → agent)

If a prompt or example shows an admin URL, rewrite mechanically:

| Wrong (browser/admin) | Right (agent token) |
|---|---|
| `/api/admin/dev/projects` | `/api/v1/agent/dev/projects` |
| `/api/admin/dev/issues` | `/api/v1/agent/dev/issues` |
| `/api/admin/clients` | `/api/v1/agent/crm/clients` |
| `/api/admin/tasks` | `/api/v1/agent/tasks` |
| `/api/admin/documents` | `/api/v1/agent/documents` |
| `/api/admin/messaging/...` | `/api/v1/agent/messaging/...` |

Rule: drop `/admin`, insert `/v1/agent`.

For the exact path of any module, fetch the live spec (public, no auth):

```bash
curl -sS https://venio.paris/api/v1/agent/openapi.json
```

This spec is generated by introspection of the actual router. Always authoritative.

## Scopes

`write:X` does NOT imply `read:X`. If you read then mutate, request both.

Common scopes:

- `read:crm`, `write:crm`
- `read:projects`, `write:projects`
- `read:tasks`, `write:tasks`
- `read:documents`, `write:documents`
- `read:internal-messaging`, `write:internal-messaging`
- `read:dev`, `write:dev` (Venio's internal dev tracker — most likely what Codex needs)
- `admin:*` (full access, master tokens only — avoid)

## Mutations require `Idempotency-Key`

Every `POST`, `PATCH`, `PUT`, `DELETE` MUST include an `Idempotency-Key` header. Generate one UUID per logical operation.

```bash
curl -sS -X POST \
  -H "Authorization: Bearer $VENIO_AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "project": "<DEV_PROJECT_ID>",
    "title": "Task title",
    "type": "TASK",
    "status": "TODO",
    "priority": "MEDIUM"
  }' \
  https://venio.paris/api/v1/agent/dev/issues
```

Behaviour:

- Same key + same body → same response (safe retry on network failure).
- Same key + different body → `409 IDEMPOTENCY_CONFLICT`.

When retrying a request that may or may not have reached the server, **reuse the same key**. Generating a new UUID on retry can produce duplicates.

## TypeScript helper (drop-in)

Use this as the standard client shape so Codex stops reinventing it across files.

```ts
const BASE = 'https://venio.paris/api/v1/agent'

async function venio<T>(
  method: 'GET' | 'POST' | 'PATCH' | 'PUT' | 'DELETE',
  path: string,
  body?: unknown,
): Promise<T> {
  const headers: Record<string, string> = {
    Authorization: `Bearer ${process.env.VENIO_AGENT_TOKEN!}`,
  }
  if (method !== 'GET') {
    headers['Content-Type'] = 'application/json'
    headers['Idempotency-Key'] = crypto.randomUUID()
  }
  const res = await fetch(`${BASE}${path}`, {
    method,
    headers,
    body: body ? JSON.stringify(body) : undefined,
  })
  if (!res.ok) {
    const text = await res.text()
    throw new Error(`Venio ${method} ${path} → ${res.status} ${text}`)
  }
  return res.json() as Promise<T>
}
```

For idempotent retries on a specific call, accept an external `idempotencyKey` parameter and reuse it across attempts.

## Common mistakes to avoid

- Calling `/api/admin/*` with a `vno_pat_` token. Wrong family. Use `/api/v1/agent/*`.
- Sending the token in `x-admin-token` or any other non-`Authorization` header. Not read.
- Omitting `Bearer ` from the `Authorization` value. Treated as missing.
- Skipping `Idempotency-Key` on mutations. Server requires it; the request will fail.
- Generating a new `Idempotency-Key` on retry of a mutation. Risks duplicate writes — reuse the original key.
- Hardcoding the token in code. Always read from env (`VENIO_AGENT_TOKEN`).
